# Sanjeevani backend — locked decisions

This file records decisions made in this backend so future sessions don't
re-litigate them. Read this before changing conventions.

## Phase

**As of 2026-08-09: Postgres-backed, not contract-and-mocks.** The backend
now reads and writes a real Neon Postgres database (`app/db.py`,
`app/db_models.py`) — the explicit decision the previous version of this
file said was required before adding a database was made, on discovering
that a teammate had already built and populated the real schema for this
exact project (16 tables, real vendors/disruptions/settlements/negotiations
— not a placeholder). See `CONTRACT.md`'s top section for the reasoning and
what changed.

Two things stayed fixture-backed on purpose, not by oversight:
`GET /forecast/{sku}` (the DB has raw `inventory_snapshots` but no
forecast/projection data — real TTM forecasting is separate, larger work)
and the `guardrails`/`briefing`/`history_summary` portion of
`GET /vendors/{id}/context` (needs real LLM-generated narrative or real
business-policy config, neither of which exists as stored data). Both still
load from `app/mocks/fixtures/*.json` via the trimmed `app/mocks/loader.py`.

**Still no real LLM/agent logic** — Sentinel/Diagnosis/Sourcing don't run;
disruptions, exposure calculations, negotiations etc. are real rows, but
nothing in this backend currently *creates* them. `agent_runs` is a real
table with no writer yet, which is why `GET /agents/status` honestly
reports every agent as IDLE.

**Single organisation, no multi-tenant auth.** Every query scopes to
`settings.org_id` (a config constant, currently the one real
`organisations` row). Don't build per-request tenant resolution without a
reason to.

**Never `create_all`, `DROP`, or `ALTER` the schema from this app.** The 16
tables already exist and are populated — `app/db_models.py` mirrors them,
it doesn't define them. If the schema needs to change, that's a
conversation with whoever owns the Neon project, not a migration this repo
runs unprompted.

## Conventions (follow everywhere, no exceptions)

- **Money**: every money field is an **integer number of paise**, named with a
  `_paise` suffix. Never a float. Use `app.schemas.money.format_inr(paise)` for
  full Indian-grouped display (`"₹62,00,000"`) and `format_inr_short(paise)` for
  short form (`"₹62.0L"`, `"₹6.2Cr"`). Every money value that ships with a display
  string alongside it (e.g. `total_paise` + `total_display`) must be generated by
  calling one of these helpers on the paise value at read time — never trust a
  stored display string, even when the DB row has one (`exposure_calcs.breakdown`
  does; it's recomputed anyway in `app/routers/disruptions.py`, since stored
  strings can drift from the paise value and this catches that class of bug
  by construction).
- **Timestamps**: timezone-aware UTC ISO-8601, field suffix `_at`, in API
  responses — every DB `datetime` needs an explicit `.isoformat()` when it
  crosses into a Pydantic schema. Inside the DB layer (writing a column),
  use `app.schemas.money.utc_now()` (returns a real `datetime`, not a
  string) — `utc_now_iso()` is for response fields only. Getting this
  backwards is a real bug, not just a style nit: a `DateTime(timezone=True)`
  column fed a string will misbehave.
- **IDs**: string UUIDv4, everywhere — matches the real DB's `character
  varying` id columns (not a Postgres `uuid` column type).
- **Envelopes**: every domain object response includes `id`, `created_at`,
  `updated_at` (see `app.schemas.common.Envelope`). Not every table has
  both columns (`settlement_batches` has neither — see
  `app/routers/settlements.py`'s `_to_settlement_batch` for the derivation
  used instead); don't assume the envelope fields map 1:1 to DB columns.
- **Enums**: UPPER_SNAKE, defined once in `app/schemas/enums.py`. Don't redefine
  or duplicate an enum value inline in another schema file. The real DB's
  string columns (`stage`, `type`, `status`, ...) are validated against
  these same enums at the API boundary — wrap DB values as
  `EnumType(row.column)` rather than trusting the raw string.

## Database layer

- **Driver**: async SQLAlchemy 2.0 over psycopg3 (`postgresql+psycopg://`).
  See `app/db.py` for why: Neon's pooled connection string is PgBouncer in
  transaction mode, which doesn't support server-side prepared statements
  persisting across pooled connections — `prepare_threshold=None` in
  `connect_args` is required, not optional, or queries fail intermittently
  under concurrent load.
- **Eager loading only.** Async SQLAlchemy does not lazy-load relationships
  safely across `await` boundaries. Every relationship a router touches
  must be `selectinload`/`joinedload`d in the query itself. `app/db_models.py`
  sets `lazy="joined"` on the small always-needed many-to-ones (e.g.
  `DisruptionEvent.vendor`); everything else needs an explicit query-level
  option — see any router for the pattern.
- **Idempotency**: `app/idempotency.py`'s `get_cached_response`/
  `store_response`, backed by the real `idempotency_records` table (unique
  index on `idempotency_key`) — replaces the old in-memory dicts. Same
  contract as before: replay the same key, get the identical cached
  response, never a duplicate side effect. This is a strict improvement —
  it now survives a process restart, which the dicts never did.
- **`VendorCandidate` → `Verification` is not a formal `relationship()`.**
  It's matched on a `(disruption_id, vendor_id)` pair rather than a single
  FK, which would need a string-evaluated composite join with a forward
  reference to work as a declarative relationship — fragile for what it
  buys. `app/routers/disruptions.py` fetches verifications for the
  disruption with a plain second query and matches them in Python instead.
  Follow that pattern rather than fighting SQLAlchemy's relationship
  string-eval namespace for a similar case.

## API shape rules

- Every response model lives in `app/schemas/`, split by domain. Routers never
  define inline response shapes — import from schemas.
- Every router file maps to one domain and is included in `app/main.py`.
- Auth: `X-API-Key` header, checked only when `REQUIRE_API_KEY=true`. Off by
  default in dev so teammates can hit endpoints immediately.
- Path spelling is intentionally inconsistent between `/api/v1/settlements/...`
  (plural, execute) and `/api/v1/settlement/...` (singular, batch/confirm) —
  this matches the locked contract in CONTRACT.md exactly. Do not "fix" this
  without updating CONTRACT.md and telling the frontend/voice teams first.

## WebSocket `/api/v1/live`

- Single global `LiveFeedManager` (`app/ws_manager.py`) holds the connection set
  and a 50-event ring buffer. On connect, the last 50 events are replayed, then
  the connection receives live broadcasts.
- Every event type is broadcast through `live_feed.broadcast(...)` — never send
  raw dicts from a router; always go through this so the ring buffer and all
  connected clients stay consistent.
- Heartbeat (`HEARTBEAT` event, no payload) fires every 20s regardless of mock
  mode. `MOCK_LIVE_REPLAY` now defaults to **false** — the scripted replay
  loop is only for local UI-only work with no DB configured, and would
  otherwise mix a fake disruption into a now-real data stream.

## Adding a new DB-backed endpoint

1. Confirm the table already exists in the real schema (`app/db_models.py`
   lists all 16) — don't add a table. If the data genuinely isn't there,
   that's a fixture-backed endpoint (see below) or a "not in scope yet"
   conversation, not a schema change.
2. Define/extend the response schema in `app/schemas/<domain>.py`.
3. Query via `Depends(get_db)` (`app/db.py`), eager-loading whatever the
   response needs (see "Database layer" above).
4. Add the route to the matching `app/routers/<domain>.py` file.
5. Update `CONTRACT.md` with the new endpoint/example and where its fields
   are actually sourced from (a straight column, a derived aggregate, a
   reconstructed value like the disruption timeline — say which).

## Adding a new fixture-backed endpoint (forecast/vendor-context style)

1. Define the response schema in `app/schemas/<domain>.py`.
2. Add/extend a fixture JSON file in `app/mocks/fixtures/`.
3. Load and validate it in `app/mocks/loader.py` (`Store.__init__`) — fixtures
   must validate against their pydantic model at startup, this is intentional
   (catches shape drift immediately instead of at request time).
4. Add the route to the matching `app/routers/<domain>.py` file, or create one.
5. Update `CONTRACT.md` with the new endpoint/example.
